03 — Diseño + API + Desarrollo

Diseñar contra el contrato real

Leer la especificación OpenAPI como material de diseño: datos disponibles, reglas de negocio, estados y casos límite antes de la primera pantalla en alta fidelidad.

Contexto

Una funcionalidad construida por completo sobre una API existente: la interfaz solo podía mostrar, filtrar y validar lo que los endpoints devolvían de verdad.

Problema

Los primeros diseños asumían campos que el contrato no exponía e ignoraban respuestas que sí devolvía. Todo lo que no era el camino feliz caía en desarrollo para inventarse a mitad de sprint.

Objetivo

Diseñar un flujo que el contrato pueda servir y especificar cada respuesta que la persona podría recibir.

Proceso

Leí la especificación OpenAPI endpoint por endpoint, mapeé cada elemento de UI a un campo, escribí las reglas de negocio junto al flujo, listé los casos límite con desarrollo y armé un inventario de estados pegado a las pantallas, no en un documento aparte.

campo amount → entero, unidades menores → máscara + validación
regla pago > saldo → bloqueado antes de la petición
409 referencia duplicada → recuperación inline, no un toast

Solución

Un flujo diseñado alrededor de lo que la API puede entregar, con catorce estados especificados —carga, skeleton, vacío, primer uso, datos parciales, validación, permisos, timeout, conflicto y fallo— cada uno con su copy y su vía de recuperación.

carga skeleton vacío primer uso parcial validación conflicto error
Impacto

Menos preguntas a mitad de sprint y ningún rediseño causado por datos inexistentes. Desarrollo revisó el flujo contra la especificación en vez de contra suposiciones.

Aprendizajes

Leer la especificación es trabajo de diseño. Una restricción encontrada temprano es material; encontrada tarde es retrabajo.
